# cut-losses — 疑难止损

> 一个 bug 修了很久还没修好，问题很可能不在 bug 本身，而在排查方向。

## 触发条件

- 同一问题连续 3 轮以上未解决
- 用户说"这个修不好"、"要不要砍掉"、"换个方案"
- AI 反复给出"已修复"但实际未修复

## 止损流程

```
1. 暂停当前修复，不要再试第 N+1 次
   ↓
2. 让两个不同的强模型分别独立排查
   - 各自给出：根本原因 + 支撑证据（复现步骤、日志、最小用例）
   - 不让它们看到对方的结论
   ↓
3. 按证据强弱对比两个结论
   ↓
4. 人做最终决策
```

### 步骤 2：独立排查

两个排查者必须是**不同的模型**。同一个模型跑两次，结论高度相关，起不到交叉验证的作用。

给每个模型相同的上下文（代码 + 问题描述 + 之前试过的修复及其失败表现），要求：

```markdown
请独立排查这个问题。之前的修复都失败了，不要默认沿用它们的前提。输出：

1. 根本原因是什么？
2. 证据：给出一条能复现或证伪这个判断的具体操作（命令、最小用例、要看的日志行），并附上你实际执行的结果。
3. 如果要修，具体怎么修？修完用什么观察结果证明修好了？
4. 这个功能在当前技术栈下是否确实可行？依据是什么？
```

不要求模型报 0-100 的置信度：模型自报的分数校准很差，拿它设阈值是假精度。比的是证据。

### 步骤 3：按证据对比

证据分三档：

- **已验证**：排查者实际跑了复现或证伪操作，结果支持它的判断
- **可验证**：给出了具体可跑的操作，但还没跑
- **推测**：只有推理，没有可执行的验证手段

| 情况 | 处理方式 |
|------|---------|
| 两边结论一致，且至少一边已验证 | 按共识方案修复 |
| 两边结论不同，至少一边已验证 | 先修已验证的那个方向，给一轮预算 |
| 两边结论不同，都是可验证 | 先把两边的验证操作都跑一遍（不改代码），再按结果归档重新对比 |
| 两边都只有推测 | 问题很可能超出当前能力，交人考虑砍掉或换方案 |

### 步骤 4：人的三种决策

1. **继续修**：有了新方向，再给 1-2 轮机会，设明确的成功标准
2. **换方案**：用不同的技术思路实现同一需求（如换库、换算法、换交互方式）
3. **砍功能**：这个功能不做了，或用更简单的方式满足核心需求

## 决策依据

做出"砍还是修"的判断时考虑：

- **开发阶段已经难以定位的问题，上线后再出现会更难修** — 维护成本是否值得
- **对模型持续提苛刻要求不一定能解决技术限制** — 有些事情就是当前做不到
- **用户真正需要的是什么** — 也许有更简单的方式满足同一需求

## 实际操作（Antigravity）

两个排查者要落在不同模型上。先用 `swarm` 的 `models` 动作查看可用模型，挑两个不同家族的：

```
swarm(action="add", name="investigator-a", model="<模型A>", brief="独立排查以下问题，输出根因 + 已执行的验证结果...")
swarm(action="add", name="investigator-b", model="<模型B>", brief="独立排查以下问题，输出根因 + 已执行的验证结果...")

# 两份结论都回来后，按步骤 3 的表格整理，向用户呈现对比和建议
```

只能用 `invoke_subagent` 时，一个用 `Model="pro"`，另一个用与之不同的档位（例如主对话模型不是 pro 时用 `Model="inherit"`）。

## 实际操作（Cursor）

在 Cursor 中，通过双标签页 + 跨模型家族实现独立排查：

```markdown
1. 暂停原会话：连续 3 轮未修好时，立刻在原 Composer/Chat 中暂停，不要继续追加修补。

2. 新建两个独立排查会话：
   - 打开两个全新的 Chat 或 Composer 标签页（Tab A 与 Tab B）。
   - Tab A 选用模型家族 A（例如 Claude 3.7 Sonnet / Claude 3.5 Sonnet）。
   - Tab B 选用模型家族 B（例如 OpenAI o3-mini / GPT-4o 或 DeepSeek R1）。
   - 注意：两边互不共享对话历史，保证排查完全独立、不带先入为主偏见。

3. 分别发送独立排查指令：
   - 将「步骤 2：独立排查」中的 Prompt 模板分别粘贴至 Tab A 与 Tab B。
   - 提供相同上下文：问题表现、复现步骤、此前尝试过但失败的方案及其错误表现。
   - 明确要求两边在终端实际运行诊断命令，提交真实验证证据（非主观猜测）。

4. 汇聚对比与决策：
   - 收集两份排查报告，对照「步骤 3：按证据对比」表格比对证据档位。
   - 将对比摘要带回主会话，由人拍板「继续修 / 换方案 / 砍功能」。
```

## pstack 联动

- 排查前读取 `principle-attack-the-premise` 的 `SKILL.md`，按它质疑之前修复共享的前提假设。
- 根因分析读取 `principle-fix-root-causes` 的 `SKILL.md` 并按它执行。
- 如果没有 pstack，按本技能的双模型对比流程独立执行。
