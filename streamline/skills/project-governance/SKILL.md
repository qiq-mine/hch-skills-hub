# project-governance — 项目治理

> 功能越做越多但效果越来越差时，问题不在单个功能，在于整个项目缺少治理。

## 触发条件

- 用户说"越来越乱"、"样式不一致"、"文档过期了"
- 审查反复指出同一类问题
- 新功能的质量明显低于早期功能

## 三件事

### 1. 高频错误写成规则

**识别信号**：
- 同一位置被审查反复指出问题
- 两个不同功能踩到同一个坑
- 某类 bug 已经修过两次

**做法**：
把注意事项写进项目的开发约束文件：Antigravity 环境写入 `AGENTS.md` 或 `.agents/rules/`；Cursor 环境写入 `.cursor/rules/*.mdc`（如 `.cursor/rules/project-rules.mdc`），让后续实现和审查自动关注。

```markdown
# 项目规则

## 数值约束
- 所有尺寸、间距、颜色必须引用设计 token，不允许硬编码数值
- 新增常量时先检查是否已有同类定义

## 错误处理
- 外部 API 调用必须设超时，失败时向用户显示可操作的提示，不吞掉异常
- 耗时超过 1 秒的操作必须可取消，不允许阻塞主线程
```

### 2. 交互规范集中维护

**问题**：已有功能用卡片单选，新功能改成下拉，用户体验割裂。

**做法**：
把颜色、间距、字号、通用组件、交互模式梳理成一份文档，作为唯一信息源：

```markdown
# UI 规范（唯一信息源）

## 选择控件
- 选项 ≤ 5 个：使用卡片单选组件 `CardSelector`
- 选项 > 5 个：使用下拉选择 `Dropdown`
- 多选：使用复选框列表 `CheckboxGroup`

## 间距
- 卡片间距：12px
- 区域间距：24px
- 页面边距：20px
```

这份文档有两个作用：
1. AI 实现新功能时查阅，保证风格一致
2. 审查时作为检查基准

### 3. 文档定期与代码巡检

**过期文档的代价**：
- AI 读了旧文档写新代码 → 发现跟实际不一致 → 浪费时间重新判断
- AI 只读了旧文档、没验证代码 → 按错误信息写新功能 → 人很难发现

**巡检流程**：

```
1. 让 AI 列出项目中所有文档文件
   ↓
2. 逐份对照当前代码检查：
   - 描述的 API/接口是否还存在？
   - 描述的流程是否还是当前实现？
   - 描述的配置项是否还有效？
   ↓
3. 对照结果分类：
   - ✅ 准确 → 保留
   - ⚠️ 部分过期 → 修正后凝练
   - ❌ 完全过期 → 删除或归档
   ↓
4. 输出巡检报告，交用户确认后执行修改
```

**巡检频率**：建议每完成一个大功能后做一次，或每 2 周做一次。

## 治理是持续的

> [!WARNING]
> 规则写完不代表问题消失。对话变长时，模型对早期输入的遵循会变差。发现偏差后继续优化规则，必要时在新对话中重新加载规则。

## pstack 联动

- 规则编码：读取 `principle-encode-lessons-in-structure` 的 `SKILL.md`，能写成 lint 或脚本检查的规则就不只写成文字。
- 代码清理：读取 `principle-subtract-before-you-add` 和 `no-comments` 的 `SKILL.md` 并按它们执行。
- 文档巡检可调用 research 子智能体批量扫描。
