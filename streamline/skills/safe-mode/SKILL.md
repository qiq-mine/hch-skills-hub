# safe-mode — 安全模式

> 程序崩溃了，用户打不开，也无法在程序里告知解决方案。这是最坏情况的最后防线。

## 触发条件

- 桌面/移动端客户端项目
- 用户说"崩溃了打不开怎么办"、"客户端崩溃恢复"
- 设计容错恢复机制时

## 问题场景

发布了一个有 bug 的版本 → 用户一打开就崩溃 → 用户需要到官网下载新版本 → 但程序打不开，无法在程序里告知解决方案 → 用户可能不知道去哪里下载 → 用户流失

## 安全模式设计

### 核心原则

**安全模式本身绝对不能崩溃。**

它是程序的最底层恢复入口，必须做到：
- 代码路径极简，不依赖可能出问题的业务模块
- 不加载可能导致崩溃的用户数据、插件、配置
- 独立于主程序的初始化流程

### 实现层次

```
程序启动
  ↓
崩溃检测（上次是否非正常退出？）  ← 必须在加载配置、插件、数据库等一切重型初始化之前
  ↓ 是
进入安全模式
  ↓
显示最小化 UI：
  - 告知用户发生了什么
  - 提供恢复选项（重置配置 / 下载新版本 / 联系支持）
  - 提供日志导出（方便排查）
```

### 崩溃检测方式

| 方式 | 原理 |
|------|------|
| **启动标记** | 启动时写一个标记文件，正常退出时删除。下次启动发现标记还在 → 上次非正常退出。注意：强杀进程、系统关机、断电也会留下标记，所以单次标记不能直接判定为崩溃，要配合下面的连续计数 |
| **连续崩溃计数** | 记录连续非正常退出次数，达到阈值（如 2 次）才进入安全模式，过滤掉偶发的强杀和断电。主程序正常运行一段时间（如 30 秒）或正常退出后清零 |
| **崩溃日志检测** | 检查系统崩溃日志，判断上次是否异常退出 |

### 安全模式 UI 模板

```
┌─────────────────────────────────────┐
│                                     │
│  ⚠️ 程序遇到问题，已进入安全模式      │
│                                     │
│  [重置配置并重启]                     │
│  [下载最新版本]  ← 直接跳转官网下载页   │
│  [导出日志]      ← 方便发给开发者排查   │
│  [联系支持]                          │
│                                     │
└─────────────────────────────────────┘
```

### 实现检查清单

- [ ] 安全模式代码不依赖任何业务模块
- [ ] 安全模式不加载用户配置文件（配置文件本身可能是崩溃原因）
- [ ] 安全模式不初始化数据库连接、网络服务等复杂依赖
- [ ] "下载新版本"链接指向固定的官网地址，不依赖动态配置
- [ ] 安全模式有独立的测试用例，确保自身不崩溃
- [ ] 连续崩溃 N 次后自动触发安全模式（N 通常设为 2）
- [ ] 崩溃检测代码在所有重型初始化之前执行
- [ ] 安全模式自己也写启动标记；如果安全模式本身也非正常退出，下次启动直接显示纯静态的兜底页面（只有官网下载链接和支持联系方式），不再进入安全模式，避免循环
- [ ] 用户点「重置配置并重启」后清零崩溃计数，再按正常流程启动

## 不只是桌面端

安全模式的思想适用于任何持久运行的客户端：

| 类型 | 安全模式表现 |
|------|------------|
| 桌面应用 | 最小化弹窗 + 恢复选项 |
| 移动 App | 启动时检测崩溃 → 清除缓存重启 / 提示更新 |
| Electron 应用 | 禁用所有插件启动 → 提示恢复 |
| CLI 工具 | `--safe-mode` 参数跳过配置加载 |

## 与 release-gate 的关系

- `release-gate`：降低发布有崩溃 bug 的概率
- `safe-mode`：万一崩溃了，用户仍有恢复路径

两者一起用，发布才真正闭环。
