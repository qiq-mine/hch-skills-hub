# delegate-execute — 分工执行

> 人和沟通模型对话，沟通模型把编码派给执行模型，保持主对话干净。

## 触发条件

- 用户说"方案确认了，开始做"、"开始执行"
- `readable-proposal` 阶段完成并得到用户确认

## 三层分工

```
用户 ←→ 沟通模型（主对话）
              │
              ├── 派发 → 执行模型（编码）
              │             │
              │             ▼
              └── 派发 → 审查模型（检查）
                             │
                             ▼
                    审查结果返回主对话
                    主对话决定修复方案
                             │
                             ▼
                    派发 → 执行模型（修复）
```

### 角色分配

| 角色 | 职责 | 模型档位 |
|------|------|---------|
| **沟通模型** | 接受需求、拆解任务、协调各方、向用户汇报 | 判断角色（主对话当前模型） |
| **执行模型** | 接受明确任务指令，输出代码 | 执行角色（Antigravity `flash` 档） |
| **审查模型** | 检查执行结果，报告问题 | 判断角色（Antigravity `pro` 档），且与执行模型不同 |

具体用哪个模型不在这里写死。装了 pstack 时按 `setup-pstack` 生成的配置选；没装时用上表的 Antigravity 档位。

### 为什么要分工

1. **主对话保持干净**：编码细节、调试日志、测试输出不会淹没人需要看的信息
2. **按长处分配**：有些模型写代码快但总结啰嗦，放在执行位可以减少人逐条阅读的负担
3. **额度分配灵活**：不同模型的配额和成本不同，可以把高频编码交给便宜的模型

## 代码审查清单

审查模型检查时，重点看：

- [ ] **业务跑通了吗**：沿用户路径端到端操作验证，不只看测试通过
- [ ] **实现是否好维护**：有没有冗余代码、复杂绕行、放着现成框架不用自行拼凑
- [ ] **测试有没有价值**：检查无意义的测试（断言常量、重复覆盖），避免浪费运行时间
- [ ] **复用了项目基础能力吗**：通用组件、工具函数等已有实现是否被充分利用

## 执行流程

```
1. 沟通模型接收 readable-proposal 确认后的方案
   ↓
2. 拆解为独立可执行的子任务
   - 每个子任务必须有：明确输入、预期输出、验证方式
   ↓
3. 逐个或并行派发给执行模型
   ↓
4. 执行完成后，派发给审查模型检查
   ↓
5. 审查结果返回主对话
   - 无问题 → 向用户汇报进展
   - 有问题 → 主对话决定修复方案，派发执行模型修复
   ↓
6. 全部子任务完成 → 进入 layered-testing 的重型回归阶段
```

## 实际操作（Antigravity）

在 Antigravity 中，分工通过子智能体实现：

```
# 主对话负责沟通和拆解
# 用 invoke_subagent 派发编码任务
invoke_subagent(TypeName="self", Model="flash", Role="执行者", Prompt="...")

# 用 invoke_subagent 派发审查任务
invoke_subagent(TypeName="self", Model="pro", Role="审查者", Prompt="...")
```

或使用 `/teamwork` 命令让 Antigravity 自动分配团队。

## 实际操作（Cursor）

在 Cursor 中，通过 Composer 会话隔离与模型切换实现三层分工：

```markdown
1. 主会话拆解（沟通角色）：
   - 在主 Chat 或主 Composer 中完成方案确认与任务拆解。
   - 将方案拆为独立子任务，每个任务明确：修改文件范围、预期行为、本地验证命令。

2. 开启独立 Composer 执行编码（执行角色）：
   - 按 `Cmd/Ctrl + I` 开启独立的 Composer 窗口/标签页（保持主会话上下文干净）。
   - 可选用响应迅速的编码模型（如 Claude 3.5 Sonnet / Composer 默认模型）。
   - 派发具体子任务，由执行模型完成代码编写与局部测试，避免冗长的调试日志污染主会话。

3. 切换强推理模型审查（审查角色）：
   - 执行模型完成后，切换到强推理/思考模型（如 Claude 3.7 Sonnet Thinking / o3-mini / DeepSeek R1）。
   - 审查模型对比当前 Git 变更（`git diff`），按「代码审查清单」做针对性审查。

4. 闭环汇报：
   - 审查发现缺陷时，将具体问题带回执行 Composer 会话修复。
   - 验证通过后向主会话汇报已验证证据，关闭执行会话，进入下一子任务。
```

## pstack 联动

- 审查环节：读取 `interrogate` 的 `SKILL.md`，按它做多模型对抗审查。
- 代码清理：读取 `no-comments` 和 `unslop` 的 `SKILL.md` 并按它们执行。
- 如果没有 pstack（技能列表里没有 `interrogate`），审查改用两个不同模型分别检查同一份代码。
