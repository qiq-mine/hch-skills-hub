# cut-losses — 疑难止损

> 一个 bug 修了很久还没修好，问题很可能不在 bug 本身，而在排查方向。

## 触发条件

- 同一问题连续 3 轮以上未解决
- 用户说"这个修不好"、"要不要砍掉"、"换个方案"
- AI 反复给出"已修复"但实际未修复

## 止损流程

```
1. 暂停当前修复，不要再试第 N+1 次
   ↓
2. 让两个强模型分别独立排查
   - 各自给出：根本原因判断 + 置信度（0-100）
   - 不让它们看到对方的结论
   ↓
3. 对比两个结论
   ↓
4. 人做最终决策
```

### 步骤 2：独立排查

给每个模型相同的上下文（代码 + 问题描述 + 之前的修复尝试），要求：

```markdown
请独立排查这个问题，输出：

1. 你认为的根本原因是什么？
2. 你对这个判断的置信度是多少？（0-100，90+ 表示很有信心）
3. 如果要修，具体怎么修？
4. 这个功能在当前技术栈下是否确实可行？
```

### 步骤 3：对比结论

| 情况 | 处理方式 |
|------|---------|
| 两个模型一致，置信度都 > 80 | 按共识方案修复 |
| 两个模型分歧，但各自置信度 > 60 | 人来判断哪个方向更靠谱，或两个方向各试一轮 |
| 两个模型都 < 60 | 这个功能可能确实超出当前能力，考虑砍掉或换方案 |
| 一个 > 80，一个 < 40 | 让高置信度的模型先试，但给它一轮的预算上限 |

### 步骤 4：人的三种决策

1. **继续修**：有了新方向，再给 1-2 轮机会，设明确的成功标准
2. **换方案**：用不同的技术思路实现同一需求（如换库、换算法、换交互方式）
3. **砍功能**：这个功能不做了，或用更简单的方式满足核心需求

## 决策依据

做出"砍还是修"的判断时考虑：

- **开发阶段已经难以定位的问题，上线后再出现会更难修** — 维护成本是否值得
- **对模型持续提苛刻要求不一定能解决技术限制** — 有些事情就是当前做不到
- **用户真正需要的是什么** — 也许有更简单的方式满足同一需求

## 实际操作（Antigravity）

```
# 派发两个独立排查的子智能体
invoke_subagent(TypeName="self", Model="pro", Role="排查者A",
  Prompt="独立排查以下问题，不要参考之前的修复方向...")

invoke_subagent(TypeName="self", Model="pro", Role="排查者B",
  Prompt="独立排查以下问题，不要参考之前的修复方向...")

# 汇总两个结论，向用户呈现对比和建议
```

## pstack 联动

- 排查方向质疑调用 `principle-attack-the-premise`（已有结论反复失败时，质疑前提假设）。
- 根因分析调用 `principle-fix-root-causes`。
- 如果没有 pstack，按本技能的双模型对比流程独立执行。
