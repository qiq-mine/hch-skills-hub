# release-gate — 发布门禁

> 重要发布条件应该是程序化限制，不是口头约定。

## 触发条件

- 用户说"准备发版"、"上线准备"、"设置发布流程"
- 项目进入持续发版阶段

## 发布检查清单

每次发布前必须通过：

### 必过门禁

| 检查项 | 如何验证 | 不过怎么办 |
|--------|---------|-----------|
| 全量测试通过 | 本地运行完整测试套件 | 修复失败的测试 |
| 无未完成的关键修复 | 检查 issue/任务列表 | 完成或推迟到下个版本 |
| 版本号已更新 | 检查版本配置文件 | 更新版本号 |
| 更新日志已写 | 检查 CHANGELOG 或发布说明 | 补写 |
| 代码已合并到主分支 | 检查 git 状态 | 合并 |

### 可选门禁（根据项目配置）

- [ ] 性能指标未退化（对比上一版基线）
- [ ] 官网/落地页版本信息已同步
- [ ] 安全扫描通过
- [ ] 内测用户反馈无阻断问题

## 程序化限制

尽可能把门禁变成自动拦截，而不是靠记忆：

```bash
# 示例：pre-push hook
#!/bin/bash
# 没跑过测试不允许推送
if [ ! -f .last-test-run ] || [ $(find .last-test-run -mmin +60) ]; then
  echo "❌ 测试超过 1 小时未运行，请先执行 make test"
  exit 1
fi

# 版本号没更新不允许推送
if ! git diff HEAD~1 --name-only | grep -q "version"; then
  echo "❌ 版本号未更新"
  exit 1
fi
```

## 回滚准备

每次发布前，确认以下回滚能力：

1. **保留上一版的发布配置**：能在 10 分钟内回退到上一个稳定版本
2. **回滚步骤文档化**：不依赖记忆，任何人按步骤都能执行
3. **回滚后验证**：回滚后跑一遍核心流程，确认恢复正常

```markdown
## 回滚步骤（模板）

1. 切换到上一版分支：`git checkout v1.2.3`
2. 重新构建：`make build`
3. 部署/分发：[具体步骤]
4. 验证：[核心流程检查]
5. 通知用户：[渠道和话术]
```

## 发布后观察

- 发布后 24 小时内关注崩溃报告、用户反馈
- 设定回滚触发条件：崩溃率超过 X%，或核心功能不可用
- 确认新版本稳定后，才清理上一版的回滚配置

## 与 safe-mode 的关系

`release-gate` 管发布流程，`safe-mode` 管发布后崩溃的恢复。两者配合：
- 发布门禁降低出问题的概率
- 安全模式提供出问题后的最后防线
