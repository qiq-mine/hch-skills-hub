# delegate-execute — 分工执行

> 人和沟通模型对话，沟通模型把编码派给执行模型，保持主对话干净。

## 触发条件

- 用户说"方案确认了，开始做"、"开始执行"
- `readable-proposal` 阶段完成并得到用户确认

## 三层分工

```
用户 ←→ 沟通模型（主对话）
              │
              ├── 派发 → 执行模型（编码）
              │             │
              │             ▼
              └── 派发 → 审查模型（检查）
                             │
                             ▼
                    审查结果返回主对话
                    主对话决定修复方案
                             │
                             ▼
                    派发 → 执行模型（修复）
```

### 角色分配

| 角色 | 职责 | 推荐模型 |
|------|------|---------|
| **沟通模型** | 接受需求、拆解任务、协调各方、向用户汇报 | 沟通能力强的模型（Claude Opus / Gemini Pro） |
| **执行模型** | 接受明确任务指令，输出代码 | 编码速度快的模型（Flash / Grok Fast） |
| **审查模型** | 检查执行结果，报告问题 | 判断力强的模型（Claude Opus / Pro） |

### 为什么要分工

1. **主对话保持干净**：编码细节、调试日志、测试输出不会淹没人需要看的信息
2. **按长处分配**：有些模型写代码快但总结啰嗦，放在执行位可以减少人逐条阅读的负担
3. **额度分配灵活**：不同模型的配额和成本不同，可以把高频编码交给便宜的模型

## 代码审查清单

审查模型检查时，重点看：

- [ ] **业务跑通了吗**：沿用户路径端到端操作验证，不只看测试通过
- [ ] **实现是否好维护**：有没有冗余代码、复杂绕行、放着现成框架不用自行拼凑
- [ ] **测试有没有价值**：检查无意义的测试（断言常量、重复覆盖），避免浪费运行时间
- [ ] **复用了项目基础能力吗**：通用组件、工具函数等已有实现是否被充分利用

## 执行流程

```
1. 沟通模型接收 readable-proposal 确认后的方案
   ↓
2. 拆解为独立可执行的子任务
   - 每个子任务必须有：明确输入、预期输出、验证方式
   ↓
3. 逐个或并行派发给执行模型
   ↓
4. 执行完成后，派发给审查模型检查
   ↓
5. 审查结果返回主对话
   - 无问题 → 向用户汇报进展
   - 有问题 → 主对话决定修复方案，派发执行模型修复
   ↓
6. 全部子任务完成 → 进入 layered-testing 的重型回归阶段
```

## 实际操作（Antigravity）

在 Antigravity 中，分工通过子智能体实现：

```
# 主对话负责沟通和拆解
# 用 invoke_subagent 派发编码任务
invoke_subagent(TypeName="self", Model="flash", Role="执行者", Prompt="...")

# 用 invoke_subagent 派发审查任务
invoke_subagent(TypeName="self", Model="pro", Role="审查者", Prompt="...")
```

或使用 `/teamwork` 命令让 Antigravity 自动分配团队。

## pstack 联动

- 审查环节自动调用 `interrogate`（多模型对抗审查），如果 pstack 可用。
- 代码清理调用 `no-comments` 和 `unslop`。
- 如果没有 pstack，审查用两个不同模型分别检查同一份代码。
