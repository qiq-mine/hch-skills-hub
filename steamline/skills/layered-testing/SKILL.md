# layered-testing — 分层测试

> 频繁跑全量测试是在烧时间。局部改动跑局部，完成后做重型回归。

## 触发条件

- 用户说"测试太慢了"、"怎么安排测试"、"测试跑不完"
- 开发过程中需要决定什么时候跑什么测试
- 需要清理无用测试

## 核心策略：分层

```
改一个函数 → 跑这个模块的单元测试          （秒级）
改一个功能 → 跑这个功能的集成测试          （分钟级）
功能全部完成 → 跑全量测试 + 端到端回归      （可能十几分钟）
准备发版 → 跑全量 + 性能测试 + 人工验收     （完整流程）
```

### 时间经济学

假设一小时内改了 10 次代码：
- **每次都跑全量**（每次 2 分钟）→ 20 分钟浪费在等测试
- **只跑对应模块**（每次 10 秒）→ 不到 2 分钟，最后跑一次全量验证

节省的 18 分钟可以多做一个功能。

## 四件要做的事

### 1. 拆分测试层

把测试按运行速度和依赖范围分层：

| 层 | 内容 | 什么时候跑 |
|----|------|-----------|
| **单元** | 纯逻辑运算、数据处理函数 | 每次改动对应模块时跑 |
| **UI/组件** | 界面组件渲染、交互响应 | 改 UI 代码时跑 |
| **集成** | 模块间协作、API 调用 | 改功能时跑 |
| **端到端** | 完整用户流程 | 功能完成后跑 |
| **性能** | 耗时指标、内存占用 | 性能优化或发版前跑 |

如果项目当前没有分层，先让 AI 把测试拆开再继续。

### 2. 反复调试路径封装成工具

已经调通过、后续还会反复用的操作路径：

- 封装成命令行工具或测试脚本，传参数即可运行
- 复杂操作（文件选择、上传等）聚合封装，供 AI 用参数调用
- 桌面软件测试增加后台运行能力，避免弹窗打断人

```bash
# 不好：每次手动操作
打开 App → 导入文件 → 选择格式 → 点击处理 → 检查输出

# 好：封装成脚本
./test-pipeline.sh --input video.mp4 --format h265 --check-output
```

### 3. 性能测试设合理目标

- 给 AI 可达到的性能目标，而不是理想化指标
- 目标不合理时，AI 可能为了达标而把代码写得更差
- 让 AI 先采集基线指标，再基于基线设优化目标

### 4. 定期清理无用测试

识别并清理以下测试：

- **断言常量**：`expect(1+1).toBe(2)` 类测试，没有实际价值
- **重复覆盖**：多个测试验证同一行为的不同表述
- **实现绑定**：测试的是内部实现细节而非外部行为，改实现就要改测试
- **永不失败**：无论代码怎么改都通过的测试

清理标准：如果删掉这个测试，有没有任何真实 bug 会因此漏掉？没有就删。

## 人 vs AI 的验证分工

| 交给 AI | 人来做 |
|---------|--------|
| 端到端自动测试 | 复杂功能手动体验 |
| 性能指标采集和分析 | 流程设计是否合理 |
| 回归检查旧业务是否被破坏 | 交互是否舒服 |
| 脚本化的重复验证 | 视觉效果判断 |

## pstack 联动

- 完成后验证调用 `prove-it-works`。
- 测试编写调用 `tdd` 和 `principle-test-behavior-not-implementation`。
- 如果没有 pstack，按本技能的分层策略独立执行。
