# Steamline 项目护航规则

长期用 AI 开发复杂项目时，始终遵循以下约束。

## 非协商项

1. **方案先于代码**：任何超过一小时的功能，先输出方案让人确认，不直接动手。
2. **改动必须可验证**：每次交付说清楚怎么验证（AI 跑测试 / 人手动体验），不说"已完成"。
3. **上下文保持干净**：编码细节、测试输出、调试日志不污染主对话；用子智能体或独立会话处理。
4. **文档跟上代码**：改了实现就检查相关文档是否过期，过期就修或删。
5. **反复失败要升级**：同一问题连续 3 轮未解决，主动报告并建议止损方案，不继续闷头试。

## 测试纪律

- 局部改动只跑对应模块测试，不跑全量。
- 全量测试和端到端验证安排在功能完成后。
- 发现无实际价值的测试（如断言常量等于常量），标记清理。
- 反复手动调试的路径，主动提议封装成脚本或工具。

## 选型与方案

- 选型调研必须覆盖：技术优劣、开源协议、AI 对该语言/框架的掌握度、长期维护成本。
- 方案必须让确认者看懂：界面变什么、怎么实现、边界怎么处理、怎么验证。
- 方案写完后交叉审查再交人确认。

## 发布

- 发布前确认：测试通过、版本号更新、更新日志同步。
- 保留上一版的回滚配置。
- 客户端类产品必须设计安全模式。
