# Archscribe 与 Web 融合

## 目标

Hybrid 不是把一张图贴进网页，而是从同一份共享内容模型生成两个阅读尺度：Archscribe 负责全局拓扑、分支和回环，Web 负责概念、比较、证据、逐步解释和交互。

## 产物路由

| 可观察条件 | 选择 |
| --- | --- |
| 主要是定义、比较、长文解释，拓扑简单 | Web only |
| 主要是全局关系、分支、故障回环和可编辑交付 | Archscribe only |
| 读者既要先看全貌，又要逐步理解细节 | Hybrid |

流程只有 1–3 个完整语义阶段时，Web 使用正常纵向滚动；4 个及以上时，流程细节使用横向 Slide。只要存在多实体依赖、分支或回环，Hybrid 仍可增加 Archscribe 总览；Slide 数量不决定是否需要总览图。

## 共享内容模型

先为每个语义阶段定义稳定 ID，再派生两种表现：

```json
{
  "id": "verify",
  "label": "验证交付",
  "input": "执行结果与质量门槛",
  "change": "判断是否满足交付条件",
  "output": "交付或回到加载/执行",
  "webSteps": ["exec-2", "recap"]
}
```

- Archscribe 的 `nodes[].id` 使用该稳定 ID。
- Web 的章节或 Slide 可以一对一或一对多映射到该 ID。
- 图的边表示状态转换；Web 文案解释转换依据与影响。
- 图中只放短标签和必要条件，完整解释留给 Web。
- 修改顺序、术语或回环时，先改共享模型，再同步两种产物。

## 页面叙事顺序

Hybrid 页面按以下顺序组织：

1. 定义：它是什么、解决什么问题、边界是什么。
2. 比较：它与 Prompt、Tool / MCP、Agent Loop 等相邻概念的区别。
3. 总览：Archscribe 展示从启动到验证的完整闭环。
4. 深挖：Web Stage 或 Slide 逐步解释选择依据、加载方式、执行和闭环。
5. 结论：回到角色分工与读者应记住的判断。

这能避免读者先看到局部细节，却不知道自己位于完整链路的哪里。

## 嵌入策略

正式单文件 HTML 优先使用 inline SVG：它可继承 HCH.HUB 颜色、响应式缩放，并能通过稳定 ID 与当前 Slide 联动高亮。Archscribe 若只输出 PNG/GIF，可在 PoC 中作为 `<img>` 引用验证构图，但不要把它当成最终单文件交付。

不要默认使用 `iframe`：它会拆开主题、键盘焦点、响应式布局与节点联动。只有需要保留完整独立运行环境、且部署允许多文件时才考虑 iframe。

若使用 SVG，给节点写入 `data-phase="verify"` 或等价属性。Slide 切换时只更新对应节点和相关边的激活状态；在 `prefers-reduced-motion` 下取消路径流动与自动过渡。

## HCH.HUB 视觉映射

页面 Token 是最终权威，Archscribe 图应适配页面，而不是反过来：

| 角色 | 建议颜色 |
| --- | --- |
| 背景 | `#05091A` |
| 主文字 | `#E2EEFF` |
| 主强调 | `#00CFFF` |
| 成功 / 通过 | `#00FF8A` |
| 风险 / 回环 | `#FF7C5C` |

若 Archscribe 当前只支持 `default` / `paper`，先选最接近的 `default` 生成结构，再在内联 SVG 或页面包装层中映射品牌 Token。不要声称原生支持尚不存在的任意主题配置。

## Archscribe 验证

1. 先运行 spec 的 validate-only 检查。
2. 渲染 PNG、GIF 或 Excalidraw，并执行 `--verify --check`。
3. 视觉检查节点文字、边标签、回环箭头和画布边界。
4. 若浏览器渲染不可用，可用 Pillow 兜底，但要记录动画能力差异。

## 跨产物验收

- 每个 Archscribe 节点至少有一个 Web 章节或 Slide 映射。
- Web 可以比图更细，但不得改变主链路顺序。
- 显式选择、语义匹配、加载、执行、观察、验证使用一致术语。
- 回环的起点、终点和触发条件一致。
- 单文件要求开启时，不残留外部图片、字体或 iframe 依赖。
- 桌面与移动端均能读懂总览；键盘和触控均能操作细节 Slide。
